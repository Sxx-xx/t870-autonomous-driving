1. 재설계 배경
--------------

t870_migration_summary.txt 기준 기존 설계는 조향과 전후진을 모두
Pixhawk RC override로 내보내는 구조였다. 실장비 확인 결과 두 가지
문제로 이 경로가 성립하지 않는다.

(1) T8 sports 차량에 STM 제어보드가 들어 있어 외부 입력이 먹지 않는다.
    Pixhawk RC override로 스로틀 값을 보내도 STM 보드가 무시한다.

(2) 조향 모터가 서보가 아니라 DC 모터다.
    노트북 코드가 Pixhawk에 값을 주면 Pixhawk가 PWM으로 변환하는데,
    그 PWM을 DC 조향모터에 그대로 주면 duty가 속도로 작용해서
    끝까지 돌아가버린다. 위치 제어가 되지 않는다.

따라서 최하단 구동 계통만 교체한다. 상위 스택
(MaRRT -> Pure Pursuit -> /cmd_vel)은 변경하지 않는다.


2. 기존 구조 대비 변경점
------------------------

                기존                          변경
  ---------------------------------------------------------------------
  조향          Pixhawk RC CH1 PWM            Pixhawk PWM -> 아두이노
                -> 조향모터 (끝까지 돌아감)    -> 포텐셔미터 위치 루프
                                              -> 조향모터

  전후진        Pixhawk RC CH3 PWM            아두이노가 전압(PWM duty)
                -> Cytron MDD20A              직접 제어, STM 보드 우회
                (STM 보드가 무시)             엔코더 속도 PI

  Pixhawk       구동 + 센서                   센서 + 조향 PWM 출력
                                              + RC 수동개입 + 페일세이프

현재 launch에 물려 있는 노드는 roboclaw_steering_node가 아니라
src/t870_control/t870_control/pixhawk_vehicle_interface_node.py 이며,
조향 RC CH1 / 스로틀 RC CH3를 모두 RC override로 내보내고 있다.
(pixhawk_vehicle_interface_node.py 128~149행)
이 노드가 교체 대상이다.

3. 확정된 최종 구조
-------------------

  [IMU / IST8310 / F9P] -> PX4 EKF2 -> MAVROS ----+
  [RPLIDAR C1] -> /scan --------------------------+
                                                  |
                                                  v
                                 MaRRT -> Pure Pursuit -> /cmd_vel
                                                  |
                    +-----------------------------+------------------+
                    | angular.z                                      | linear.x
                    v                                                v
            MAVROS RC override                              USB 시리얼 (목표 km/h)
                    v                                                v
            Pixhawk PWM 출력  ----------------------------->  Arduino Uno
                                                             |
                                                  +----------+----------+
                                                  |                     |
                                          조향 위치 루프          구동 속도 PI
                                          (PWM 캡처 +            (엔코더 +
                                           포텐셔미터)            드라이버 duty)

역할 분담:

- Pixhawk 6C Pro
  - IMU / IST8310 / F9P 융합, PX4 EKF2 -> MAVROS odometry (대체 불가)
  - 조향 목표값을 PWM으로 출력
  - RC 조종기 수동 개입 경로 확보
  - 노트북 사망 시 페일세이프

- Arduino Uno (두 루프 모두 담당)
  - 조향: Pixhawk PWM 펄스폭을 목표 조향각으로 해석,
          포텐셔미터로 실제 각도 읽어 목표에 도달하면 모터 정지
  - 구동: 엔코더로 속도 측정, 속도 PI로 드라이버 duty 출력
  - 아두이노는 이 둘만 한다. 경로계획/라이다 E-Stop은 노트북,
    위치/자세 추정은 Pixhawk 담당.

- 노트북 (ROS 2)
  - MaRRT 경로 계획, Pure Pursuit 추종, /cmd_vel 생성
  - angular.z -> MAVROS RC override
  - linear.x -> USB 시리얼로 Uno에 목표 속도 전달


4. 구동 PI를 아두이노에 두는 이유
---------------------------------

속도 PI는 피드백(엔코더)과 출력(duty)이 같은 칩 안에 있어야 한다.

엔코더를 아두이노가 읽는데 duty를 Pixhawk가 내면 제어 루프가
  아두이노 -> 시리얼 -> 노트북 -> MAVLink -> Pixhawk -> PWM
을 한 바퀴 돌아야 하고, 20~50 ms 지연과 지터가 붙는다.
저속 주행(0.5~2 km/h) 튜닝이 사실상 불가능해진다.

Pixhawk를 구동에 쓸 때의 장점(RC 수동개입, 페일세이프)은
조향 경로가 이미 Pixhawk를 지나가므로 그쪽에서 확보된다.

5.3 엔코더 전기 사양

  4선: 빨강=VCC, 검정=GND, 초록=A상, 파랑=B상 (쿼드러처)
  모터 몸통 부착, 모터 뒷축에 원형 자석 -> 홀 자석식
  INPUT_PULLUP 직결 상태로 정상 동작 -> 5V 출력으로 판단

  홀 자석식은 모터 1회전당 7~16 PPR 수준이라 광학식(100~2000 PPR)의
  약 1/100 해상도다. 감속비를 넉넉히 잡아도 Uno가 감당한다.
  따라서 ESP32 등 추가 MCU 불필요. Uno 한 대로 조향+구동 모두 처리.

5.4 모터 드라이버

  조향: Cytron MD20A   (단채널, DIR + PWM)
  구동: Cytron MDD20A  (DIR + PWM, 조이스틱 테스트로 전후진/속도 확인 완료)

  두 드라이버 모두 PWM 상한 20kHz.


6. Arduino Uno 최종 핀 배치
---------------------------

  핀     용도                        현재 배선 상태
  ------------------------------------------------------------
  D2     엔코더 A상 (INT0)           D5 -> 이동 필요
  D3     엔코더 B상                  D6 -> 이동 필요
  D7     조향 DIR                    그대로
  D8     Pixhawk PWM 입력 (PCINT0)   미배선
  D9     조향 PWM (Timer1)           D5 -> 이동 필요
  D10    구동 PWM (Timer1)           D9 -> 이동 필요
  D11    구동 DIR                    D8 -> 이동 필요
  A0     조향 포텐셔미터             그대로

  여유: D4, D5, D6, D12, D13, A1~A5

핀 선정 근거:

- 엔코더를 D2/D3에 둔 이유
  Uno의 외부 인터럽트(INT0/INT1)는 D2/D3뿐이다.
  엔코더는 펄스율이 가장 높으므로 여기를 배정한다.

- Pixhawk PWM 입력을 D8에 둔 이유
  ATmega328P는 핀 체인지 인터럽트(PCINT)를 20핀 전부에서 지원한다.
  PCINT는 포트 단위로 벡터가 묶여 있어 지연/지터가 크지만,
  50Hz 저속 신호인 PWM 캡처에는 충분하다.
  D8 = PB0 = PCINT0.

- 모터 PWM을 Timer1(D9/D10)에 몰아둔 이유
  - Timer0(D5/D6)은 millis(), delay()와 타이머를 공유한다.
    주파수를 바꾸면 시간 함수가 전부 깨진다. 모터에 쓰면 안 된다.
  - Timer1은 프리스케일러 한 줄로 주파수를 올려 가청소음을 없앤다.

      TCCR1B = (TCCR1B & 0b11111000) | 0x02;   // 약 3.9kHz
      // 0x01 = 31.25kHz 이지만 MD20A/MDD20A 상한 20kHz를 넘는다
      // 기본값 0x03 = 488Hz 는 모터에서 가청소음이 난다

  - D9/D10이 같은 Timer1이라 두 모터 PWM 주파수가 한 번에 잡힌다.


7. 조향 제어 현황
-----------------

상태: 자동 중앙 복귀 동작 확인. Pixhawk PWM 입력은 미구현.

동작:
  포텐셔미터 값을 읽어 CENTER_POS(295)로 되돌린다.
  오차 크기에 비례해 PWM을 조절한다(P 제어).
  좌우 스팬이 비대칭이므로 방향별 스팬으로 매핑한다.

방향 로직 (검증됨):
  pot 값이 클수록 좌측 (644 = LEFT_END)
  currentPos > CENTER_POS  ->  좌측에 있음  ->  우회전
  currentPos < CENTER_POS  ->  우측에 있음  ->  좌회전

미확인:
  RIGHT_DIR = LOW 가 실제로 우회전인지 미검증.
  반대로 돌면 RIGHT_DIR / LEFT_DIR 의 HIGH/LOW만 교환한다.

주요 상수:
  MIN_PWM      = 60     정지마찰 극복 최소 duty
  MAX_PWM      = 100    캘리브레이션 중 상한 (낮게 시작)
  DEADBAND     = 10
  STALL_DELTA  = 3      이만큼도 안 변하면
  STALL_MS     = 500    이 시간 넘으면 스톨 래치


8. 구동 제어 현황
-----------------

상태: 시리얼로 목표 km/h 입력 -> 램프 -> PI 제어 동작.
      피드포워드 계수 실측 및 게인 튜닝 미완료.

동작:
  노트북(현재는 시리얼 모니터)이 목표 km/h를 준다.
  ACCEL_RATE / DECEL_RATE로 램프를 걸어 부드럽게 목표를 옮긴다.
  엔코더로 실제 속도를 측정해 PI로 duty를 만든다.

주요 상수:
  ACCEL_RATE          = 0.5   km/h per sec
  DECEL_RATE          = 0.7
  MAX_SPEED_KMH       = 2.0   첫 시험용. 문서 권장 0.5 m/s = 1.8 km/h
  REVERSE_GUARD_KMH   = 0.3   이 이상 굴러가는 중엔 방향 반전 금지
  STOP_THRESHOLD_KMH  = 0.05
  CMD_TIMEOUT_MS      = 1500  명령 워치독
  MIN_PWM             = 45
  MAX_PWM             = 200
  CONTROL_INTERVAL    = 100ms (10Hz)
  SPEED_FILTER_N      = 3     속도 이동평균 탭 수


9. 발견하고 수정한 버그 목록
----------------------------

9.1 조향 스케치

  (1) 센서 이상 검사가 죽은 코드였다
      if (currentPos < 0 || currentPos > 670)
      analogRead()는 절대 음수를 반환하지 않으므로 앞 조건은
      항상 거짓. 정작 위험한 단선(0 근처)을 못 잡았다.
      -> FAULT_LOW / FAULT_HIGH 로 교체.
         스파이크 오검출 방지를 위해 연속 5회 발생만 인정.

  (2) 소프트 리밋이 없었다
      우측 끝이 ADC 0이라 와이퍼가 트랙 끝을 때린다.
      -> SOFT_RIGHT(30) ~ SOFT_LEFT(620) 밖으로는 구동하지 않는다.

  (3) 스톨 보호가 없었다
      포텐셔미터 고장이나 링키지가 걸리면 오차가 안 줄어들어
      무한정 최대 PWM으로 밀어붙인다. 모터가 탄다.
      -> 구동 중 pot이 500ms간 안 변하면 정지 래치.
         시리얼 'r' 로 해제.

  (4) PWM 핀이 D5(Timer0)였다
      millis()/delay()와 타이머 공유. 주파수 조정 불가.
      기본 490Hz라 가청소음.
      -> D9(Timer1)로 이동 후 3.9kHz로 상향.

  (5) 좌우 비대칭 미반영
      map(error, DEADBAND, 300, ...) 으로 300을 하드코딩.
      실제 스팬은 좌우가 다르다 (현행 5V 기준 좌 506 / 우 447).
      -> 방향별 스팬을 인자로 받도록 변경.
         스팬을 상수 계산식(LEFT_END - CENTER_POS 등)으로 두면
         캘리브레이션 값만 고쳐도 매핑이 따라온다.

9.2 구동 스케치

  (1) 감속이 되지 않았다  [가장 심각]
      int pwmValue = MIN_PWM + (int)controlOutput;
      pwmValue = constrain(pwmValue, MIN_PWM, MAX_PWM);
      controlOutput이 음수여도(실제 속도 > 목표) PWM이 MIN_PWM
      아래로 못 내려간다. 오버슈트를 잡지 못하고, 목표를 낮춰도
      최소 45 duty가 계속 나간다.
      -> 하한을 0으로 수정. MIN_PWM은 "구동할 때의 최소 duty"로만 적용.

  (2) 시리얼 블로킹 중 엔코더 카운트를 놓쳤다
      D5/D6은 인터럽트 핀이 아니라 폴링이었는데,
      printStatus()가 115200bps로 약 100바이트를 출력한다.
      TX 버퍼(64B)를 넘으면 loop가 수 ms 블로킹되고 그 동안
      엣지를 놓친다. 실제 속도가 과소 측정되면 PI가 계속 더 밟는다.
      -> D2(INT0) 인터럽트로 이동.

  (3) 명령 워치독이 없었다
      노트북이 죽거나 USB가 빠져도 마지막 명령 속도로 계속 달린다.
      ROS 브리지를 붙이는 순간 치명적.
      -> CMD_TIMEOUT_MS(1500ms) 초과 시 정지.
         벤치 테스트용으로 'b' 입력 시 토글 가능.

  (4) 주행 중 방향 반전 = 역전 제동
      rampSpeed 부호가 바뀌면 즉시 DIR_PIN을 뒤집는다.
      바퀴가 굴러가는 중이면 역전 제동이 걸려 드라이버와 모터에
      큰 전류가 흐른다.
      -> REVERSE_GUARD_KMH(0.3) 이상으로 굴러가는 중에 반대 명령이
         오면 일단 0을 목표로 감속. 정지 후에야 반대로 간다.

  (5) abs(deltaCount) 로 방향 정보를 버렸다
      경사에서 뒤로 밀릴 때 전진 명령 중이면 실제로는 후진인데
      "전진 중"으로 읽어 PI가 출력을 줄인다. 더 밀린다.
      -> 부호 있는 속도 사용. ENCODER_SIGN 상수로 부호 교정 가능.

  (6) anti-windup 이 constrain 뿐이었다
      -> 조건부 적분으로 교체. 적분을 더했을 때 출력이 포화되면
         누적하지 않는다.

  (7) 포화 시 역방향 제동 위험
      -> PI 출력이 0 이하면 duty 0(관성주행)으로 처리.
         반대 방향 duty를 주지 않는다.

  (8) 저속 양자화
      -> 3탭 이동평균 추가 (완화만, 근본 해결은 4체배)

  (9) 정지 상태에서 printStatus 를 호출하지 않았다
      -> 항상 출력하도록 변경.


10. 속도 PID 튜닝 절차
----------------------

10.1 D항은 넣지 않는다

미분항은 속도의 변화율을 본다. 1 km/h에서 100ms당 5 counts뿐이라
+-1 count 양자화가 +-0.2 km/h 노이즈로 잡히는데, 여기에 미분을 걸면
노이즈만 증폭되어 PWM이 떤다. 차량 속도 루프는 관성이 커서
애초에 D가 거의 필요 없다.

  -> PI + 피드포워드 구조를 쓴다.

10.2 피드포워드가 게인 튜닝보다 중요한 이유

DC 모터는 역기전력 때문에 duty와 속도가 거의 선형이다.

    duty = FF_OFFSET + FF_GAIN x |목표 km/h|

이 식만 맞춰두면 PI는 경사/부하 같은 외란만 잡으면 된다.
FF가 없으면 적분기가 매번 0에서부터 필요한 duty를 전부 쌓아올려야
해서 응답이 느리고 오버슈트가 크다.

  튜닝 순서:  FF 실측  ->  Kp  ->  Ki

10.3 STEP 1 - 개루프 특성 측정

바퀴를 띄우고, 'b'로 워치독을 끈 상태에서 진행한다.
'p' 명령으로 duty를 직접 인가하고 5초 후 안정된 Actual을 기록한다.

    명령     duty    측정 Actual (km/h)
    ------------------------------------
    p50       50     ______
    p70       70     ______
    p90       90     ______
    p110     110     ______
    p130     130     ______

  안 도는 구간이 데드존이다.
  도는 구간 중 두 점을 골라 계산한다.

    FF_GAIN   = (duty2 - duty1) / (speed2 - speed1)
    FF_OFFSET = duty1 - FF_GAIN x speed1

  예) p70 -> 0.8 km/h,  p130 -> 2.0 km/h 인 경우
      FF_GAIN   = 60 / 1.2 = 50
      FF_OFFSET = 70 - 50 x 0.8 = 30

10.4 STEP 2 - FF만으로 확인

  Kp = 0, Ki = 0 으로 두고 1.0 입력.
  Actual이 0.8~1.2 사이면 FF가 맞은 것이다.
  크게 벗어나면 STEP 1을 다시 한다.

10.5 STEP 3 - Kp

  0.05부터 2배씩 올린다.

    목표 도달이 느림          -> Kp 올림
    PWM 떨림 / 속도 출렁임    -> Kp 내림 (직전 값의 절반)

  진동이 시작되는 값의 절반이 적정선이다.

10.6 STEP 4 - Ki

  0.02부터 2배씩 올린다.

    목표에 영원히 못 닿음     -> Ki 올림
    오버슈트 후 천천히 복귀   -> Ki 내림

10.7 주의

  - 바퀴를 띄운 상태의 게인과 지면 주행 게인은 다르다.
    부하가 없어서 FF_GAIN이 실제보다 작게 나온다.
    지면에서 STEP 1을 한 번 더 해야 한다.
  - 지면 측정은 반드시 저속(1 km/h 이하)부터, 사람이 옆에서
    잡을 수 있는 상태로 한다.
  - 튜닝이 끝나면 'b'로 워치독을 반드시 다시 켠다.


11. 시리얼 프로토콜 (설계 예정)
-------------------------------

  노트북 -> 아두이노 :  목표 속도 (km/h)
  아두이노 -> 노트북 :  실측 속도, 조향각, 고장 상태

상향 명령에는 속도만 실린다.

14. STM32 순정 제어보드 처리
----------------------------

14.1 원칙

소프트웨어로는 STM32의 제어권을 막을 수 없다.
물리적으로 끊었는지가 전부다.

"우회한다"는 말은 배선을 끊는다는 뜻이지, 코드로 무시한다는
뜻이 아니다.

14.2 가장 위험한 시나리오 - H브리지 병렬

STM32 보드와 MDD20A가 같은 모터 단자에 병렬로 물려 있으면
아래가 발생한다.

  - 한쪽이 HIGH를 밀고 다른 쪽이 LOW를 당기면 배터리 단락 경로가
    생긴다.
  - 라이드온 보드는 페달을 떼면 보통 전기 브레이크(모터 양단 단락)를
    건다. 그 순간 MDD20A 출력이 그대로 단락된다.
  - 두 드라이버가 모두 파손된다. 퓨즈가 먼저 나가면 다행이다.

  [필수 확인]
  구동 모터 선 2가닥과 조향 모터 선 2가닥이 지금 어디에 물려 있는지
  눈으로 확인한다. MDD20A / MD20A 단자에만 가 있고, STM32 보드로
  가던 선은 잘렸거나 커넥터가 빠져 있어야 한다.
  전원을 넣기 전에 확인할 것.

14.3 "지금 잘 돈다"가 안전을 보장하지 않는다

조이스틱 테스트에서 정상 동작했다는 것은 그 순간 STM32가 대기
상태였다는 뜻이지, 앞으로도 개입하지 않는다는 보장이 아니다.

STM32가 갑자기 개입할 수 있는 조건:

  - 가속 페달을 밟았을 때
  - 2.4GHz 부모 리모컨 신호를 받았을 때
  - 배터리 저전압을 감지했을 때
  - 자체 워치독 타임아웃
  - 전원 재인가 후 초기화 시퀀스

14.4 STM32가 하던 일과 대체 방안

  기능                        필요   대체
  ---------------------------------------------------------------
  모터 H브리지 구동            X     MDD20A / MD20A 로 대체 완료
  가속 페달 입력               X     자율주행이라 불필요
  전후진/속도 단수 스위치      X     ROS 가 /cmd_vel 로
  조명 / 사운드 / 계기판       X     기능상 불필요
  전기 브레이크                X     관성주행(coast) 방식 선택
  소프트 스타트                O     해결됨 - ACCEL_RATE 램프
  2.4GHz 부모 리모컨 정지     필수   14.5
  배터리 저전압 컷오프        필수   14.6
  과전류 보호                 필수   14.7
  메인 전원 릴레이            권장   물리 차단 스위치
  조향 포텐셔미터 급전        확인   14.8
  충전 중 주행 방지            X     운용으로 커버

14.5 비상정지 - 가장 큰 손실

부모 리모컨이 사실상 유일한 하드웨어 정지 수단이었다.
현재 계획된 E-Stop은 전부 소프트웨어다.

  - 라이다 감지        -> 노트북이 판단
  - 시리얼 워치독      -> 아두이노가 판단

아두이노가 멈추거나 코드가 무한루프에 빠지면 둘 다 무력하다.
PWM 핀은 마지막 duty를 유지한 채로 차가 계속 간다.

소프트웨어 밖에 있는 정지 수단이 반드시 필요하다.
우선순위 순:

  1. 무선 비상정지 릴레이 (24V 대전류)
     배터리 주회로를 끊는다. 부모 리모컨 역할을 그대로 대신한다.
  2. 물리 킬스위치
     차량에 손이 닿는 거리에서 시험할 때.
  3. Pixhawk RC 페일세이프
     조향은 커버되지만 구동은 커버되지 않는다.

  [주의] 3번의 구멍
  조향은 Pixhawk PWM 경로라 RC 조종기로 뺏을 수 있지만,
  구동은 아두이노 시리얼 경로라 RC로 개입할 수 없다.
  1번이나 2번이 반드시 있어야 한다.

14.6 배터리 저전압 보호

24V 배터리를 과방전시키면 납축은 수명이 급감하고, 리튬이면
영구 손상되거나 위험하다.

저항 2개로 아두이노가 대신할 수 있다.

  배터리 + ──[ 100k ]──┬── A1
                       │
                    [ 15k ]
                       │
                      GND

  분압비 = (100k + 15k) / 15k = 7.67
  24V -> 3.13V 로 안전하게 내려온다.

  const float VDIV = (100000.0 + 15000.0) / 15000.0;
  const float BATT_CUTOFF_V = 21.0;   // 24V 납축 기준

  float readBattery() {
    return analogRead(A1) * (5.0 / 1023.0) * VDIV;
  }

주행 중 순간 전압 강하(sag)로 오작동하지 않도록
임계 이하가 3~5초 지속될 때만 정지 래치를 건다.
리튬이면 셀 수에 맞춰 컷오프 전압을 다시 잡는다.

14.7 과전류 보호 - 퓨즈는 선택이 아니다

STM32에 있던 전류 제한이 사라진다. 스톨 시 수십 A가 흐른다.

  회로            퓨즈
  --------------------------------------------
  구동 모터       40A  (모터 개수/정격 확인 후 조정)
  조향 모터       10A
  로직            3A   (아두이노 / Pixhawk)

여유되면 ACS712 / ACS758 전류센서를 A2에 물려 소프트 전류 제한을
두면 좋다. 퓨즈가 나가기 전에 duty를 줄일 수 있다.

14.8 조향 포텐셔미터 급전  [해결 완료 2026-08-20]

측정 결과 양 끝 단자 사이 전압이 3.27V 였다.
(3.27 / 5.0 x 1023 = 669, 관측 최대범위 670과 일치)

원인은 (a) STM32 급전도 (b) 트랙 부분사용도 아니었다.
STM32 를 이미 뺀 상태에서 벤치 배선을 아두이노 3V3 핀에
물려두고 실험 중이었던 것이다.
-> STM32 숨은 의존성은 존재하지 않는다.

그래도 5V 로 이설했다. 두 가지 이유다.

  (1) 분해능 1.53배 (총 가동폭 624 -> 953 counts)
  (2) 비율측정(ratiometric) 복구
      Uno 의 3V3 은 5V 에서 LDO 로 만든 별도 레일이라 AVCC 와
      독립적으로 흔들린다. 그 +-2% 가 670 x 0.02 = +-13 counts 로,
      당시 DEADBAND(10) 보다 컸다. 조향각이 안 변해도 제어기가
      오차를 봤다고 판단해 모터를 긁을 수 있는 크기다.
      포텐셔미터와 ADC 기준이 같은 5V 가 되면 공급 변동이
      수학적으로 상쇄된다.

이설 후 겪은 증상 (기록):
  급전만 바꾸고 스케치 상수를 그대로 두자 조향 가동범위가 줄었다.
  스케일이 1.53배 커졌는데 SOFT_LEFT(620) 가 그대로라 좌회전이
  전체의 60% 지점에서 막혔고, FAULT_HIGH(680) 는 정상 좌회전(최대 991)을
  단락으로 오판했다. CENTER_POS(311) 도 진짜 중앙(485) 보다 우측이라
  중립이 치우쳤다.
  -> ADC 단위 상수는 하나도 빠짐없이 함께 갱신해야 한다.
     PWM 단위 상수(MIN_PWM/MAX_PWM)와 시간 상수(STALL_MS)는 그대로 둔다.

엔코더는 무관하다. A/B 상은 디지털 펄스라 급전 전압이 세는 값을
바꾸지 않는다. COUNTS_PER_REV = 157 은 재측정 대상이 아니다.
다만 노이즈 마진(HIGH 문턱 0.6 x 5V = 3.0V)과 INPUT_PULLUP 역류를
생각하면 엔코더도 5V 급전이 맞다.

14.9 MDD20A 용량 확인

24V 라이드온은 보통 후륜 좌우에 구동 모터가 2개다.

  - 모터 2개를 MDD20A 한 채널에 병렬로 물리면 전류가 2배가 된다.
  - MDD20A는 채널당 연속 20A / 피크 30A.
  - 250W 모터 2개면 정상 주행 약 21A, 스톨 시 60A 이상.

이 경우 한 채널로는 부족하다. MDD20A는 듀얼 채널이므로
모터를 하나씩 각 채널에 물린다.
코드도 두 채널을 같은 duty로 구동하도록 수정해야 한다.

14.10 대안 - STM32를 반만 살리기

모터 출력만 끊고 STM32 보드는 전원 계통용으로 남기는 방법이 있다.
메인 릴레이, 배터리 보호, 프리차지를 그대로 쓸 수 있어
추가 부품이 줄어든다.

다만 STM32가 모터가 안 물린 상태를 고장으로 보고 전원을
끊어버릴 수 있다. 실험으로 확인한다.

  1. 모터 선만 분리
  2. 전원 인가
  3. 기판 LED가 정상인지, 몇 분 후에도 전원이 유지되는지 확인

유지되면 이 방법이 편하다. 보호 회로가 꺼지면 완전히 떼는 게 맞다.

14.12 확인 필요 항목

  1. 구동 모터가 몇 개인가 (MDD20A 채널 배분이 달라진다)
  2. 배터리가 납축인가 리튬인가 (컷오프 전압 기준)
  3. 부모용 리모컨이 있는 모델인가 (수신 경로 재활용 가능성)
  4. 구동/조향 모터 선이 STM32에서 분리되었는가
  5. STM32 보드에 아직 전원이 들어가는가 (기판 LED)
  6. 포텐셔미터 양 끝 단자 전압이 5V인가 3.3V인가
     [완료] 3.27V 였고 아두이노 3V3 배선이 원인. 5V 로 이설 완료.
            STM32 의존성 없음. 14.8 참조.


결론
----

STM 보드 우회와 DC 조향모터 문제로 최하단 구동 계통을 재설계했다.
Pixhawk는 센서/측위와 조향 PWM 출력 및 안전 계층으로 남고,
Arduino Uno 한 대가 조향 위치 루프와 구동 속도 PI를 모두 담당한다.

엔코더가 홀 자석식(157 count/rev)으로 확인되어 추가 MCU 없이
Uno로 충분하다. 조향 포텐셔미터는 5V 이설 후 실측값
(38 / 485 / 991, 총 가동폭 953)을 확보했다. 다만 중앙값 485는
지면 직진 주행으로 재확인이 필요하다.

조향과 구동 각각의 테스트 스케치가 동작하며, 두 스케치에서
발견한 버그 14건을 수정했다. 남은 큰 조각은 Pixhawk PWM 캡처와
두 스케치의 통합, 그리고 ROS 시리얼 브리지 노드다.

STM32 순정 보드는 사용하지 않아도 되지만, 그 보드가 조용히 맡고
있던 안전 기능 세 가지를 우리가 떠안게 된다. 비상정지(부모 리모컨),
배터리 저전압 보호, 과전류 보호다. 이 중 소프트웨어로 대체 가능한
것은 저전압뿐이고 나머지 둘은 하드웨어가 필요하다.
소프트웨어 E-Stop만으로는 아두이노가 멈췄을 때 차를 세울 수 없다.

다음 단계는 개루프 FF 실측(10.3)으로 구동 PID를 완결하는 것이다.
다만 지면 주행 전에 14.12의 확인 항목 6가지를 먼저 마쳐야 한다.
