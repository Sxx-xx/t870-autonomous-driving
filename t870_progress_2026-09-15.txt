[출발 시 조향이 확 꺾이던 문제 - 해결]

증상: AUTO 로 올리자마자 우측으로 크게 꺾고 경로를 이탈. 반복 재현.

원인 1 - IMU heading 이 76도 틀렸다.
  09-14 에 corrected_imu 가지를 열면서 MAVROS 의 /mavros/imu/data yaw 가
  ENU 절대방위이므로 imu_yaw_offset_rad = 0.0 이 맞다고 가정했다.
  실측은 달랐다. 정지 상태에서 corrected_imu 가 -3.09 rad 을 말했는데
  차가 움직이자 gps_course 는 1.81 rad 이었다. 76도 차이.
  그 heading 으로 alpha 를 계산하니 -30도가 나와 우측으로 꺾었고,
  GPS course 가 들어오는 순간 +53도로 뒤집혀 좌측 풀락으로 튀었다.

원인 2 - route_tangent 도 21도 틀렸다.
  IMU 를 끈 뒤에도 같은 증상이 남았다. route_tangent 는 "차가 경로 방향을
  향한다"는 가정인데, 실측에서 그 가정이 21도 틀렸다.
  route_tangent 2.09 rad vs 실제 heading 1.72 rad.
  그 21도 때문에 alpha 가 -25도로 계산되어 우측으로 꺾었다. 실제 heading
  으로 계산하면 alpha 는 +1.8도, 즉 직진이 맞았다.

수정:
  use_imu_heading            False   IMU heading 사용 안 함
  route_tangent_max_steer_rad 0.0    추측 heading 으로는 꺾지 않는다
  startup_straight_sec       3.0     AUTO 전환 후 3초간 조향 0 고정
  minimum_course_speed_mps   0.10    course 확보를 앞당김 (0.30 -> 0.18 -> 0.10)

  heading 을 모르는 동안은 완전히 직진으로만 기어간다. 추측값으로 꺾을
  권한 자체를 없앴다. 실측 확인: route_tangent 구간 조향이 정확히 0.000.

주의: 그래서 출발 시 차를 경로 위에 경로 방향으로 세우는 것이 중요해졌다.
  틀어져 있으면 course 가 잡힐 때까지 그 방향으로 직진한다.

[GPS fix 품질 전달 - 신규]

smc2000_gps_node 가 GGA 품질을 전부 STATUS_FIX 하나로 뭉뚱그리고 있었다.
RTK 와 7 m 오차의 DGPS 를 구분할 방법이 없었다.

  GGA 품질 -> NavSatStatus
    0 측위불가 -> STATUS_NO_FIX   (-1)
    1 단독측위 -> STATUS_FIX      ( 0)
    2 DGPS     -> STATUS_SBAS_FIX ( 1)
    4 RTK Fix  -> STATUS_GBAS_FIX ( 2)
    5 RTK Float-> STATUS_GBAS_FIX ( 2)

follower 에 minimum_fix_status 추가 (기본 2 = RTK). 그 미만은 위치를
받아들이지 않는다. 7 m 틀린 위치로 조향을 계산하느니 멈추는 쪽이 낫다.
launch 인자로도 노출했다: minimum_fix_status:=1 이면 DGPS 까지 허용.

품질이 바뀌면 로그도 남는다:
  GPS fix quality RTK float -> DGPS. A drop out of RTK steps the reported
  position by several metres.


[LiDAR 분리 - 신규]

launch 인자 lidar_safety_enabled (기본 true). false 로 주면
  require_lidar            true -> false
  estop_distance_m         0.50 -> 0.01
  dynamic_stop_distance_m  2.00 -> 0.01
이 되어 LiDAR 가 주행에 전혀 개입하지 않는다. GPS 추종만 따로 측정할 때 쓴다.

주의: 이 상태에서는 장애물 앞에서 전혀 멈추지 않는다. 빈 공터에서
조종기를 손에 들고 할 것. MANUAL 로 내리는 것이 유일한 정지 수단이다.

참고 - 현재 구조에서 "LiDAR 로 회피"는 구현돼 있으나 검증되지 않았다.
  gps_path_follower (GPS 만) --/cmd_vel/gps--+
  MaRRTPathPlanNode (/scan) --/waypoints----+-> rrt_avoidance_mux -> gps_safe
  t870_tracker --/cmd_vel/rrt---------------+
  rrt_avoidance_mux 는 RRT 경로가 0.20 m 이상 옆으로 비키면 그쪽으로
  전환하고 0.10 m 이하로 돌아오면 GPS 로 복귀한다.
  다만 MaRRTPathPlanNode 가 실내 벤치 설정이다:
    planning_distance 2.0 m, obstacle_max_range 2.5 m,
    indoor_lidar_mode True, world_frame 'laser'
  2 m 앞만 보므로 9 km/h 에서는 회피 기동이 불가능하다. 실주행에 쓰려면
  8~10 m 로 늘리고 프레임을 odom 으로 바꿔야 한다.
  현재 실제 동작하는 장애물 대응은 회피가 아니라 E-stop(급정지)이다.


[노드가 자꾸 죽던 원인 - 해결]

증상: launch 를 띄워도 AUTO 가 안 되고, 노드 목록이 3개뿐이거나
  arduino_drive_node 가 없다. 하루 종일 반복됐다.

원인: remote_mode_control_node 가 웹 제어용 8080 포트를 연다. launch 를
  Ctrl+C 로 끄거나 터미널 창을 닫으면 이 노드만 고아로 살아남아 8080 을
  계속 물고 있고, 다음 launch 의 새 인스턴스가
    OSError: [Errno 98] Address already in use
  로 1.5초 만에 죽는다. 이 노드가 /cmd_vel 을 발행하므로 없으면 차가
  절대 움직이지 않는다. 더 나쁜 것은 좀비가 계속 STOP 을 발행해서
  현재 arduino_drive_node 와 연결도 안 된 채 모드를 잠근다는 점이다.

왜 고아가 되나: node.stop() 은 KeyboardInterrupt 를 받아야 실행된다.
  터미널 창을 닫으면 SIGINT 가 아니라 SIGHUP 이 가고, ros2 launch 가 그걸
  자식에게 정리 신호로 전달하지 못하면 자식이 고아로 남는다.
  launch 부모만 kill 해도 같다. kill -9 는 종료 핸들러를 아예 못 돌린다.

대책: t870_cleanup.sh 를 만들었다.
  bash t870_cleanup.sh
  SIGINT 로 정상 종료를 먼저 시도하고 5초 안에 안 죽으면 SIGKILL.
  그 다음 8080 포트와 시리얼 포트 4개를 전부 확인해 보여준다.
  MAVROS 는 건드리지 않는다.

종료 요령: 터미널 창을 바로 닫지 말고 Ctrl+C 후 process finished 메시지가
  다 올라올 때까지 2~3초 기다릴 것. 다시 띄우기 전 cleanup 스크립트 실행.


[Arduino 펌웨어]

AUTO_KP 16.0 -> 20.0 (MANUAL 은 22.0 그대로). 업로드 완료.
  arduino-cli 없이 avr-g++ 7.3.0 + avrdude 8.0.0 으로 직접 빌드/업로드했다.
  Flash 39.6%, RAM 50.3%.

주의: 최고속도는 Kp 로 안 올라간다. control = ff + Kp*err + Ki*I 이고
  상한이 200 인데, 10 km/h 에서 ff 만 185 를 요구해 여유가 15 뿐이다.
  ff = 6.4 + 17.9 * 목표속도 인데 이 계수는 PWM 10->0.20 km/h,
  PWM 15->0.48 km/h 두 점을 20배 외삽한 값이라 신뢰도가 낮다.
  속도를 실제로 올리려면 5~9 km/h 구간에서 FF 를 재캘리브레이션해야 한다.

[분석 시 반드시 먼저 할 것]  (09-14 메모에서 이어짐)

tracking CSV 는 조종기가 MANUAL 이어도 follower 가 계속 기록한다.
state 가 TRACKING 이라고 해서 차가 ROS 제어로 움직인 것이 아니다.

판별: 조향 명령 대비 실제 선회량을 부호 포함해 비교한다.
  dheading/dt = -v * tan(delta) / L
  2초 창으로 (실제 방위변화 / 예상 방위변화) 중앙값을 본다.
  0.4 이상이면 AUTO, 0 근처면 MANUAL 이거나 조향이 바퀴에 안 갔다.

그리고 tracking CSV 의 행이 끊긴 구간을 먼저 찾을 것.
  stop() 은 tracking 행을 쓰지 않는다. 따라서 elapsed_sec 이 크게 점프한
  구간은 follower 가 멈춘 구간이고, 대부분 GPS fix 가 stale 해진 것이다.
  이번 RTK 끊김도 이 방법으로 찾았다.
