확인:  python3 path_to_qgis.py gps_recordings/p1.csv
       python3 path_qgis_project.py gps_recordings/p1.gpkg --open

2. [해결] RTK 끊김  <- 동적 모델이 Stationary 였다
===============================================================================
증상
  주행 중 GGA 품질이 RTK Fix/Float -> DGPS 로 떨어진다. 고속 직진 11초쯤,
  급선회면 즉시. 정차/보행 중에는 안 끊긴다.

결정적 단서
  끊기는 동안 위성 12개, HDOP 0.62 가 미동도 없다 (모니터 1134샘플 min=max).
  NMEA 스트림도 안 끊긴다. 즉 측정은 멀쩡한데 항법 필터가 해를 버리는 것.

원인
  u-blox 동적 모델이 2 (Stationary). 수신기가 안 움직인다고 가정하는 모델이라
  주행 동특성을 잡음으로 보고 억누른다.

조치
  /usr/bin/python3 ubx_config.py --set-automotive
  dynModel 4 (Automotive) 로 바꾸고 플래시에 저장. 되돌리기는 --set-model 2.
  u-center 는 윈도우 전용이라 못 쓴다. ubx_config.py 가 UBX 이진 메시지를
  직접 주고받는다. ROS 스택을 끄고 돌려야 한다 (시리얼은 하나만 열린다).

결과
  146초 주행 끊김 0회. 이후 주행도 0회.

이미 되어 있어서 손댈 필요 없던 것
  고도각 마스크 10도.
  위성군 6개 전부 켜짐 (GPS, SBAS, Galileo, BeiDou, QZSS, GLONASS).
  UART 대역폭 문제는 해당 없음. u-blox USB 포트(cdc_acm)라 보드레이트가
  무시된다. 스크립트는 38400, ROS 노드는 115200 으로 여는데 둘 다 동작한다.

헛다리 짚은 것들 (기록용)
  진동/안테나 커넥터, USB 허브 대역폭, 포트 할당 꼬임, 코너 감속으로 인한
  속도 불일치. 전부 데이터로 기각됐다.
  - USB: 커널 로그 2.5시간에 u-blox/Arduino/라이다 재연결 0회.
  - 속도 불일치: GPS 도플러와 엔코더가 끊기는 순간까지 0.03 m/s 이내 일치.
  - 장소: 끊긴 지점 29곳이 무게중심에서 평균 45 m 흩어져 있었다.

3. [해결] heading 이 route_tangent 으로 떨어짐  <- RMC 가 0.02 Hz
===============================================================================
증상
  주행 중 heading_source 가 gps_course -> route_tangent 으로 바뀌고,
  route_tangent_max_steer_rad = 0.0 이라 조향이 정확히 0 으로 묶인다.
  경로는 휘는데 차는 직진해서 그대로 이탈한다. 04:04 주행에서 6.12 m 밖으로
  나갔다.

원인
  follower 의 heading 은 /gps/velocity 에서 나오고, smc2000_gps_node 는
  그걸 RMC 문장에서만 뽑았다. 그런데 이 수신기는
      VTG  4.00 Hz
      GGA  4.00 Hz
      RMC  0.02 Hz   <- 50초에 한 번
  RMC 만 쓰면 gps_course_hold_sec(3.0) 이 매번 만료된다.
  09-14~15 에 "route_tangent 60~79%" 로 고생하던 것도 전부 이것이었다.

조치
  smc2000_gps_node 에 VTG 파싱 추가. VTG 가 4 Hz 로 같은 정보(진북 방위 +
  대지속도)를 준다. 수신기 설정 변경 없이 이미 나오는 문장을 쓴 것이다.
  RMC 파싱도 그대로 두었다. 정지 중에는 VTG 방위가 빈 칸이라 안 내보낸다.

  publish_vtg_velocity(): 필드 1=진북 방위(도), 7=km/h

결과
  04:39 주행에서 주행중 heading_source 가 gps_course 889샘플,
  route_tangent 0샘플.

  QGIS 에서 내보낸 98점 파일. 앞 83점은 p1 과 좌표가 완전히 동일(0.000 m),
  뒤 15점은 QGIS 에서 새로 찍은 것이다.

    1. 새 15점이 fid 순서로 파일 맨 뒤에 붙었는데 실제 위치는 경로 한가운데다.
       행 83~88(6점)은 p1 idx 48~50 옆, 행 89~97(9점)은 idx 57~59 옆.
       파일 순서대로 달리면 idx 82 에서 30.3 m 를 건너뛴다.
    2. route_error 는 가장 가까운 '웨이포인트' 까지의 거리라, 30 m 공백
       한가운데면 15 m 가 되어 maximum_route_error_m(10.0) 을 넘고
       STOP_ROUTE_ERROR 로 선다.
    3. idx 94 에 반지름 2.11 m 코너. 조향한계 0.24 의 138% 라 물리적으로
       못 돈다.
  덧붙여 새 점들은 lat/lon 이 비고 UTM 만 있다. follower 는 UTM 을 먼저
  쓰므로 로드는 되지만 target_speed 도 비어서 그 15점만 런치 기본값이
  걸린다(속도가 뒤섞인다).

[QGIS 내보내기 함정 - 두 방향 다 있다]
  09-15 에 기록한 것은 "utm 컬럼이 옛값으로 남는다" 였는데, 이번은 반대로
  "lat/lon 이 비고 utm 만 채워진" 경우였다. QGIS 프로젝트 CRS 가 무엇이냐에
  따라 어느 쪽이 채워지는지 달라진다. 어느 쪽이든 두 값이 일치하는지
  확인하고 쓰는 편이 안전하다.

[구분자 텍스트 레이어로 CSV 를 QGIS 에 올릴 때]
  X=utm_easting_m, Y=utm_northing_m 로 넣으면 지오메트리 CRS 를
  EPSG:32652 (WGS 84 / UTM zone 52N) 로 지정해야 한다. 기본 EPSG:4326 으로
  두면 508054 를 경도로 읽어 아무것도 안 그려진다. CRS 칸의 지구본
  아이콘을 눌러야 전체 목록이 나온다(콤보에는 최근 쓴 것만 보인다).
  longitude/latitude 컬럼을 쓰면 EPSG:4326 그대로라 실수할 여지가 없다.
